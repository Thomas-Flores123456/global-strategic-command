## 0. 一句话合同

**凡是"开工后要消耗游戏时间才能完成的生产类活动"，统一抽象为一条事务（Transaction）；`<timePast>` 时钟是唯一推进事务进度的发条；事务完成必须过三色对账门才能入役。**

## 1. 第一章 · 立项动机与现状诊断

### 1.1 病根

- `QueueItem`（`schema.ts`）当前只有 `type/item/base/progress/eta` 五个字段。`progress` 是 0~100 裸数字，`eta` 是自由字符串——**没有任何引擎推进它们**，全靠 LLM 每楼自觉重报，本质是"叙述驱动"而非"模型驱动"。
- LLM 报进度天然不可靠：跳报、漏报、超报（一楼过去 2 小时坦克造好了 5 辆）均无物理约束。
- `timePastParser.ts` 已交付（parseTimePast / advanceCalendar 等四个纯函数），但发条空转——没有齿轮组消费 Δt。

### 1.2 已存在的"半成品事务"（本设计的统一对象）

| 现存机制 | 位置 | 事务视角 |
| :--- | :--- | :--- |
| 建造/研究/生产队列 | `schema.ts` QueueItem＋`parsePipeline.upsertQueues` | 事务主体，v1 直接升级 |
| `<数据更新>` 补丁管线 | worldbookDataFiler（Phase 6 已交付） | 广义事务（提交→审核→落地/驳回），**v1 不动** |
| `<生产>` 三色对账门 | CTRL-RECONCILE-01（规划中） | 事务的提交/冲突检测阶段，改挂本地基 |

### 1.3 v1 边界（Q3 驾驶员已认可 · 🔴 红线）

- **v1 只覆盖四类耗时事务**：`建造`（建筑）、`研究`（科技）、`生产`（单位/易耗）、`改装`（retrofit）。
- **明确不进 v1**：机娘入档、`<数据更新>` 补丁、动态归档、雷达/侦察、移动/部署、维修（维修走 `repair_rate` 常态带宽，属工况引擎辖区）。
- 广义统一（把补丁管线等归拢进事务框架）登记入 Future Backlog，须独立立项，防分形展开。

## 2. 第二章 · 事务状态机（冻结对象）

```text
                       ┌──────────────┐
  排队 queued ────────→│ 进行中 active │────→ 待对账 settling ────→ 已完成 done
   │   （带宽空闲即入）  └──────────────┘        （进度≥100%，          （三色门 MATCH/
   │                        │                  等 LLM <生产> 声明）      UNDERRUN 认领后）
   │                        │
   └────────┬───────────────┘
            ▼
       已作废 cancelled（驾驶员取消 / 三色门驳回 / 前置坍塌）
```

### 2.1 状态语义

| 状态 | 语义 | 谁能迁入 | 谁能迁出 |
| :--- | :--- | :--- | :--- |
| `queued` | 已立项已扣本钱，等产线带宽 | 玩家下单（前端）或 LLM 叙述立项（解析管线） | 引擎（带宽空闲自动升 active） |
| `active` | 正在消耗时间推进 | 引擎 | 引擎（进度满→settling）；取消→cancelled |
| `settling` | 物理进度已满，等叙事对账 | 引擎 | 三色门（MATCH/UNDERRUN→done；OVERRUN 拦截挂起原地不动） |
| `done` | 已入役/已生效，资产落账 | 三色门 | 终态 |
| `cancelled` | 作废；按 ECON-02 §8"回炉只返工料当量 G"退款 | 驾驶员/三色门 | 终态 |

### 2.2 状态机四条铁律

1. **只有引擎能动 progress**：LLM 与前端 UI 均不得直接写进度数字；LLM 的 `<生产>` 声明只是对账输入，不是进度写入。
2. **时间是唯一燃料**：progress 推进只发生在 `<timePast>` Δt 结算时刻，公式见第四章；没有 Δt 就没有进度。
3. **done 必过对账门**：settling→done 只能由三色裁决产生，防"LLM 说造好了就造好了"。
4. **终态不可逆**：done/cancelled 不得复活；返工＝新开事务。

### 2.3 队列调度权：LLM 调度令（Q6 · 二轮收束新增）

**动机**：产线带宽有限时谁先造谁后造是叙事级决策（前线告急先出坦克、憋科技先保研究），天然适合 LLM 在剧情中裁量；但若放任 LLM 直接改队列数组，等于交出账本写权，违背铁律 1。

**解法：调度令（dispatch order）——LLM 只能下"指令"，引擎负责"执行"**，与 `<生产>` 声明同构：都是"输入给引擎的申请单"，不是"直接写账本"。

#### 2.3.1 调度令报文（随楼层标签进入解析管线）

LLM 在正文中以既有队列报文的扩展形式声明优先级意图（不新增标签，复用 `队列` 标签通道，解析管线识别新字段）：

```text
<队列>
- 项目: 天启坦克
  调度: 置顶          // 或「置底」「暂缓」「恢复」
- 项目: 磁暴步兵
  调度: 暂缓
</队列>
```

四种调度动词（枚举收口，其余值进隔离区）：

| 动词 | 引擎语义 | 状态影响 |
| :--- | :--- | :--- |
| `置顶` | 移到同 base 同 type 队列首位；若产线满，抢占最后升格的 active（被抢占者退回 queued，**进度保留**） | active/queued 均可作用 |
| `置底` | 移到队列末位；若目标是 active，退回 queued（进度保留），空位由队首递补 | 同上 |
| `暂缓` | 标记 `hold=true`：带宽空位跳过它不升格；已 active 则退回 queued＋hold | 新增字段 hold |
| `恢复` | 清除 hold，按当前位置正常竞争带宽 | — |

#### 2.3.2 三条安全约束（🔴）

1. **调度令永不触碰 progress/spent_minutes**：被抢占/暂缓的事务进度冻结保留，恢复后从原进度续跑——挪顺序≠重造；
2. **调度令不能作用于 settling/done/cancelled**：待对账与终态事务不参与调度，违令进隔离区留痕（R 系列 warn）；
3. **驾驶员优先**：前端 UI 的手动调序（后续 UI 任务）与 LLM 调度令同走引擎调度接口，但 UI 指令即时执行、LLM 指令随楼层结算执行；同楼冲突时以驾驶员 UI 操作为准。

#### 2.3.3 数据模型增量

QueueItem v2 增补一个字段（并入 §3.1 字段表）：

```text
  hold: boolean   // 暂缓标记，default false；hold=true 时带宽升格跳过
```

队列先后次序即数组顺序（`queues` 数组本身有序），不新增显式 priority 数字——LLM 与引擎都只做"移动"操作，避免优先级数值通胀（人人都是 999）。

#### 2.3.4 前馈闭环

`<当前工程日程>` 前馈注入（RECONCILE 辖区）中同步呈现队列顺序与 hold 态，让 LLM 看得见自己上一楼调度令的执行结果，形成"下令→看结果→再调整"的闭环，而不是盲下令。

## 3. 第三章 · 数据模型：QueueItem v2（Q1=A · 原位扩充）

### 3.1 字段表

在现有 `QueueItem` 上**新增全部带默认值的可选字段**，旧五字段语义不变：

```text
QueueItem v2 = {
  // ── 既有字段（零破坏）──
  type:     '建造' | '研究' | '生产' | '改装'   // 枚举扩一项「改装」
  item:     string                             // 项目名（对齐 catalog/别名词典）
  base:     string                             // 所属基地
  progress: number 0~100                       // 语义收紧：仅引擎写（§2.2 铁律1）
  eta:      string                             // 降级为展示缓存：引擎按剩余工期格式化回填

  // ── v2 新增（全部 default，旧档零迁移成本）──
  status:    'queued'|'active'|'settling'|'done'|'cancelled'  // default 'active'
  started_at: string   // 游戏内日历时刻 ISO，default ''（空=旧档，首次结算时补记）
  total_minutes: number // 总工期（分钟），default 0（0=未知，见 §3.3 工期来源）
  spent_minutes: number // 已消耗工期（分钟），default 0
  qty:       number    // 批量数（生产类），default 1
  qty_done:  number    // 已下线数（批次流水），default 0
  cost_paid: boolean   // 立项时是否已扣款，default true（旧档视为已扣）
  min_days_lock: number // 物理硬下限（天），default 0（=不锁），供 2STAGE 引擎钳制
  hold: boolean        // 暂缓标记（§2.3 调度令），default false
}
```

### 3.2 兼容性合同（对三个既有消费方）

| 消费方 | 现用法 | v2 影响 |
| :--- | :--- | :--- |
| `parsePipeline.upsertQueues` | LLM 报队列→别名对齐→upsert/结项 | 新字段全 default 可省略，LLM 楼层报文**格式零变化**；结项语义改挂 settling（见 §5.2） |
| `ConsoleBuildGrid.vue` | 显示 `${q.progress}%` | 零破坏；后续可增显 status 徽章（独立 UI 任务） |
| `ConsoleQuickActions.vue` | 查 `type==='研究'` 占用 | 零破坏；建议升级为 `status==='active'` 过滤（随实现任务） |

- Zod 迁移链：全部新字段 `.default()`，`#0 楼 stat_data` 逐字节零注入原则不变（对齐 CTRL-RES-SCHEMA-01 先例，toStrictEqual 钉死）。

### 3.3 工期唯一来源（与 ECON-02 会师 · 🔴 红线）

**`total_minutes` 不得拍脑袋**，按优先级取：

1. 条目 `<数据>` 块显式工期字段（如 `assembly.min_days`、巨构分期表）；
2. **ECON-02 §4.1 统一式反算**：`目标天数 = 产物价 ÷ 该梯级建造带宽（credits/日）`，天数×1440＝分钟；
3. 兜底：该产物所在目标天数带（ECON-02 §4.3）中值，并在事务上打 `estimated` 记号（落 eta 展示为「约 N 日」）。

`min_days_lock` 取条目 `min_days`（若有），供两段式引擎钳制"算力无限也不可短于物理下限"。

### 3.4（F7·2026-09-25 增补）· 升格带宽门与出生语义

- **出生端（解析层）**：`upsertQueues` 新建队列事务显式落 `status:'queued'`——升格一律走带宽升格门（第四章流水线），不再直接 active。
- **回检端（引擎层）**：`settleTransactions` 在 ③（Δt 积分→settling）与 ④（queued 升格）之间新增 **③′ active 带宽回检**：既成 active 逐一过 lane 并行上限＋同 type 全局上限，超限者与未开通槽者降格回 queued（progress/spent 保留、`demoted(gate_recheck)` 留痕）——绕过升格门出生的 active（旧默认/AI 直写/人工注入）不再遗传到下一楼层。
- **次序**：③→③′→④。降格楼层度已按 Δt 记账不吞，次轮起冻结；同一事务不重复降格。
- **兼容性红线**：§3.1 的 `status` 默人值保持 `'active'` 不动（v1 旧档零迁移合同）；调度令「不碰进度」铁律不受③′影响。

## 4. 第四章 · 时间推进结算流水线（每楼一次）

```text
LLM 回楼正文
  → timePastParser.parseTimePast(text)        // 已交付，Δt 分钟（失败兜底 60）
  → advanceCalendar(clock, Δt)                // 已交付，全局日历步进
  → 事务引擎 settleTransactions(state, Δt):    // 本设计新立
      对每条 status==='active' 的事务：
        1. eff = 工况引擎综合效率（operationEngine 已交付：低电/受损/停机→产线降速）
        2. spent_minutes += Δt × eff
        3. progress = min(100, spent_minutes / total_minutes × 100)
        4. 生产类批量：qty_done = floor(spent_minutes / 单件工期)（批次流水，先下线先入役候审）
        5. progress≥100 → status='settling'
      先执行本楼调度令（§2.3：置顶/置底/暂缓/恢复，只挪顺序与 hold，不碰进度）
      对每条 status==='queued' 且 !hold 的事务（按数组顺序）：
        产线带宽有空位（同 base 同 type 的 active 数 < 并行上限）→ 升 active，补记 started_at（升格带宽门 §3.4：开通门×槽容量×tier 双重上限统一裁决）
      §F7-修订：升格前先做③′ active 带宽回检——既成 active 逐一过 lane/全局上限，超编者与槽未开通者降格回 queued（progress/spent 保留，demoted(gate_recheck) 留痕）
  → 三色对账门（CTRL-RECONCILE-01）：
      比对 LLM <生产> 声明 vs settling 队列
        MATCH    → done，资产入账
        UNDERRUN → 按实认领部分 done，余量退回 active
        OVERRUN  → 拦截挂起，出 UI 纠偏横幅（CTRL-UI-CHRONO-01）
```

### 4.1 全局时钟落点

- `stat_data` 新增顶层可选字段 `clock: { day: number, time: string }`（游戏内第 N 天＋当日时刻），`.default()` 挂载、旧档零注入；`advanceCalendar` 的输出是唯一写入方。
- 前馈注入（RECONCILE 辖区）：向提示词挂 `<当前工程日程>`＝active/settling 事务的倒计时清单，让 LLM 知道"什么还没造好"，从源头减少 OVERRUN。

#### 4.1.1 《当前工程日程》格式冻结稿（v2 · 条令体 · 2026-09-29 驾驶员冻结）

- **注入机制**：案A 平行 scheduleRunner（复刻 advisoryRunner 范式，`GENERATION_AFTER_COMMANDS` 时机，`injectPrompts`/`uninjectPrompts` 一次性注入，挂载点中控悬浮窗 index.ts init/teardown）；不设行数上限。
- **两级骨架**：基地（bases 数组序）→ 序列（laneKeyFor 输出，占用/上限照实呈现）；战区科研调度单列一节（槽位制，含未开通槽的世界内理由）；lane 内事务按数组序（=优先级）。
- **产线同源原则（红线）**：文本的产线分组直接消费引擎 laneKeyFor 的真实输出＋显示名映射，禁文本另立分类——生产多产线槽位归 CTRL-PROD-LANE-01（已登记，排本任务后）。
- **语域**：《世界书文风与受控质感编写规范》总参条令体——世界内工程调度通报；管线词（槽位/带宽/token）一律翻成世界内因果表述；零说教、零臆造数值（一切数字来自事务真源）。
- **条目句式**：`· 名称——{状态谓语句}`（破折号连接）。状态谓语对照：在产/在研「进度X%；尚需T」（批次加「已下线n/N台；节拍t」三段式）；待对账「实体已就绪，待战区呈报收讫确认」（＝等待 `<生产>` 声明，唯一保留的指令性暗示）；排队「已立项待产/待研，列于X之后」＋暂缓「奉令暂缓」；槽未开通挂序列头「X未建成，序列未开通」；工期未知「工期未核定，暂不排定时限」；停摆（eff≤0）「因工况中断，进度冻结」。
- **倒计时措辞**：沿用 fmtMinutes；效率投影表述「按当前供给折算，尚需T（供给率N%，已按实计）」。
- **空态**：空基地列「（当前无在编工程）」；全空「当前各基地与科研序列均无在编工程」。
- **文案模板**：状态谓语句集中为模板常量集（scheduleCopy.ts 或同级），与渲染逻辑分离，便于驾驶员后续调文案不动逻辑。

### 4.2 纯函数边界

`settleTransactions` 必须是纯函数：`(state, Δt, effContext) → { nextState, events[] }`，零 Pinia、零宿主 API，与 operationEngine/timePastParser 同规格，单测可全覆盖。

## 5. 第五章 · 与既有管线的接缝

### 5.1 立项入口（双轨）

- **前端下单**（中控台建造网格点击）：立即扣款（ECON-02 出账）→ 建 `queued` 事务 → cost_paid=true；
- **LLM 叙述立项**（解析管线 upsertQueues 撞见新队列项）：建事务但 `cost_paid=false` 记账务欠条，随三色门或体检对账补扣——防 LLM 白嫖立项。

### 5.2 结项语义改挂

现行 `parsePipeline` 中"LLM 报科技完成→队列结项 splice 删除"的路径，v2 后改为：**LLM 完成声明→找到对应事务→若 status 为 settling 走 MATCH 入役；若仍 active 且差距小（≤1 日带宽）按 UNDERRUN 宽容认领；差距大即 OVERRUN 拦截**。删除式结项仅保留给 cancelled。

> 勘误（2026-09-29 · A′ 定案）：「差距小按 UNDERRUN 宽容认领」的实现口径＝**宽容不静默**——引擎对一切「物理未完工却声明完工」统一 OVERRUN 拦截；≤1 日带宽的时序差距由 CTRL-UI-CHRONO-01 横幅默认高亮「自动顺延时间」一键兑现（补差额 Δt 经 settleFloor 正常结算 → 重对账自然 MATCH）。引擎 v1 口径零改动，active→done 仍非法。

### 5.3 不动区（🔴）

- `worldbookDataFiler`／`PanelDataPatches`：现有裁决三通道保持独立，v1 不并入事务框架；
- `girlFiler`／归档管道：不动；
- 维修/抢修：走 `repair_rate` 常态带宽（虚拟产出池），不建事务。

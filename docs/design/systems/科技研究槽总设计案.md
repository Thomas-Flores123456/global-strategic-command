## 1. 第一章 · 立项动机与现状诊断

### 1.1 病根

- `CTRL-TXN-SCHEMA-01` 已交付的 `settleTransactions` 带宽门按 `base+type` 分道（laneKey），研究类事务 base 恒空串——**全部研究挤在同一条 lane，并行上限默认 1，等价于全局单研究槽**。
- 既有 canon 早已不是单槽制：
  - 《异能穿越模拟器v1.0》06a：「通用研究占对应品类建筑的**附属研究槽**，为独立研究轨道」；

### 1.2 本设计的角色

把散落在世界书总则里的"专属研究槽"叙述**升格为通用注册表制度**，并与事务引擎会师——槽位裁决器是喂给 `SettleOptions` 的一组纯回调，不是引擎的新分支。

### 1.3 红线（🔴）

- 设计案先行：confirmed 前不碰任何代码/schema/世界书 JSON；
- 不重写 `transactionEngine` 核心：状态机白名单、结算四步顺序、调度令语义一概不动，仅允许 §5.2 定义的两个**可选、默认恒等**的接缝回调加法；

## 2. 第二章 · 槽的来源：混合开通制（Q1=C · 冻结）

### 2.1 三层语义分工

| 层 | 归谁管 | 内容 |
| :--- | :--- | :--- |
| **槽的存在与归属** | 静态注册表（§3） | 哪条线属于哪个槽、槽容量几何——制度自带，不随建筑增减 |
| **槽的开通** | 锚定建筑在场检测 | 注册表声明每槽的锚定建筑；锚定建筑不在场＝槽冻结（线内研究只能 `queued` 排队，不能升 `active` 开研） |
| **单项研究的资格** | 各研究项自身 `need_buildings`/`prereq` | 现行机制不变，不与槽二次记账 |

### 2.2 开通语义的引擎表达（零改动）

槽冻结不需要引擎新概念：`parallelLimitFor` 回调对未开通槽返回 **0**，引擎现行 `Math.max(0, limitFor(txn))` 天然表达"有队无道"——排队保留、升格封死。锚定建筑建成后回调返回 1，队首自动升格。拆除锚定建筑时在研项目按引擎既有语义处理：active 事务不被强制打断（进度冻结等价于 eff 缩放与 hold 的既有工具，实现任务给出具体策略提案，默认＝保持 active 但下一楼结算时因槽容量归 0 而由裁决器下达「暂缓」调度令退回 queued，进度保留）。

### 2.3 与 06a 附属表述的归一化解释

06a「品类建筑附属研究槽」自本设计起解释为：**槽由制度注册，品类锚定建筑负责"开通"该槽**——附属＝开通依赖，而非建筑供给槽数量。世界书措辞对齐（06a 及各线总则如需微调）登记为勘误债，confirmed 后另开门处理，本任务不碰 JSON。

## 4. 第四章 · 并行上限：双层门（Q3 改判=C · 冻结）

全分槽制下没有"主槽"可扩容，原 Q3（主槽 T2→2）作废，改判为**双层上限**：

### 4.1 第一层 · 槽内恒 1

每槽容量恒 1，线内串行——农畜业「上限 1」落盘约定升格为全表通则。**任何槽不随 tier 扩容**。

### 4.2 第二层 · 全局研究并行上限（随 tier 门放宽）

| 基地科技资格 | 全局同时 active 研究数上限 | 判定依据 |
| :--- | :--: | :--- |
| T1 | **2** | 默认 |
| T2 | **4** | 战斗实验室在场（catalog 现行 T2 资格门） |
| T3 | **不限**（受开通槽数天然封顶） | 阵营 T3 门卡（苏联四张国家工程卡／盟军五件套） |

- 全局上限管"同时开研总数"，槽管"每线一项"——早期稀缺（11 槽也只能同时开 2 项，逼出取舍）、中期放宽、后期全开（上限＝已开通槽数）；
- tier 判定由裁决器侧 `techTier(state)` 纯函数推导，引擎只吃数字；
- **tier 判定以进度最远的阵营为准（驾驶员裁决 2026-09-22）**：各阵营科技解锁进度不同，全局研究门取所有在场阵营中的最高档——任一阵营战斗实验室在场即全局 T2；任一阵营达成其 T3 资格门（苏联四张国家工程卡／盟军五件套）即全局 T3。T3 门卡当前无机读依据，实现停在 T1/T2 两档（RSLOT-IMPL-01 回执已声明）；**T3 接线合同**＝门卡机读化后经 `makeGlobalLimitFor` 的 `techTierOf` 注入口实现「任一阵营达标即 T3」判定，引擎与注册表均零改动；
- 升格取位规则：全局有空位时按 `queues` 数组序扫描（与引擎现行第④步一致），先到先得；LLM/驾驶员可用既有调度令（置顶/暂缓）影响顺序——**不新增调度动词**。

## 5. 第五章 · 数据模型与引擎会师（Q4 · 冻结）

### 5.1 占用状态：派生不落盘（Q4①）

- 槽位占用**完全由 `queues` 中 `type==='研究' && status==='active'` 的事务推导**（单一事实源），不新增任何 `stat_data` 字段——零 schema 改动、零 #0 楼注入风险、与 TXN-SCHEMA-01 文件锁零冲突；
- 注册表本体落新文件 `researchSlots.ts` 纯函数模块（研究名/line → 槽 ID＋容量＋锚定建筑＋开通判定＋全局上限），不进变量树、零 Pinia、零宿主 API，与 operationEngine/transactionEngine 同规格。

### 5.2 引擎接缝合同：乙案 laneKeyFor（Q4③ · 🔴 边界）

`transactionEngine.ts` 允许且仅允许两个**可选、默认恒等/无限**的接缝加法（在 TXN-SCHEMA-01 驾驶员验收＋锁释放后实施）：

```text
SettleOptions 增补：
  laneKeyFor?: (txn) => string
    // default：现行 `${base}\u0000${type}`（非研究路径行为逐字节零变化）
    // 裁决器注入：研究事务 → `research:${slotId}`；其余事务 → 默认值
  globalLimitFor?: (type) => number
    // default：Infinity（现行无全局限语义零变化）
    // 裁决器注入：type==='研究' → techTier 门（T1=2/T2=4/T3=Infinity）
```

- **诚实边界声明**：「零重写核心」指不改状态机白名单、结算四步顺序、调度令语义、进度积分公式；两个默认恒等的可选回调属接缝扩展。`laneKey` 内部函数改为读回调，`countActive`/升格门/调度令抢占均经同一 laneKey 通道，语义自动一致；
- 升格门在现行「lane 内 active < parallelLimitFor」之上叠加「同 type 全局 active < globalLimitFor」双重检查（≈8 行加法）；
- 既有 34 项 transactionEngine 单测零破坏为硬验收线（默认路径恒等）。

### 5.3 裁决器职责清单（researchSlots.ts）

| 导出 | 职责 |
| :--- | :--- |
| `SLOT_REGISTRY` | §3.1 全表常量（slotId/name/lines/anchor/capacity） |
| `slotFor(line \| researchName)` | line→槽 ID 映射，未注册兜底 `slot.main`＋warn |
| `makeLaneKeyFor(catalogIndex)` | 生成注入引擎的 laneKeyFor 回调 |
| `makeParallelLimitFor(state)` | 研究 lane：锚定建筑在场→1，不在场→0（冻结）；非研究：委托现行规则 |
| `makeGlobalLimitFor(state)` | 研究 type→tier 门数字；其余→Infinity |
| `slotBoard(state)` | 派生只读视图：各槽 {开通状态, 在研项, 排队数}——供 UI/前馈日程消费 |

### 5.4 LLM 报文合同：零变化（Q4②）

- `<队列>` 报文格式**零变化**：研究项按 `type+item` 全局唯一 upsert（parsePipeline 现行），多研究并行时按研究名天然对号；
- **LLM 不需要也不允许报槽位**——槽归属由裁决器查注册表决定，防谎报槽位白嫖并行；报文中出现槽位类字段一律忽略并 warn 留痕；
- 前馈闭环：`<当前工程日程>` 注入（RECONCILE 辖区）按 `slotBoard` 分槽呈现在研/排队/冻结状态，让 LLM 看得见"哪条线的道被占着"，从源头减少乱开研叙述。

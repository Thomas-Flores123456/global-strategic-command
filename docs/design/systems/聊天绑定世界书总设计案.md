## 0. 一句话合同

**本角色卡的每一个聊天对应且只对应一本「聊天档案书」；一切"随剧情生长"的世界书写入必须经绑定守卫核验目标后落入当前聊天的这本书；核验任一环失败即 fail-closed 拒写留痕，绝不静默写入别的书。**

## 1. 第一章 · 立项动机与病根

### 1.1 病根：写入目标与聊天无绑定

现有写入器（girlFiler 双书入档、worldbookDataFiler 数据块补丁）写入目标全部是**硬编码书名的全局共享书**：

| 写入器 | 目标书 | 定位方式 |
| :--- | :--- | :--- |
| `girlFiler.fileDossier` | 《机娘·能力档案》＋《剧情·北坡纪事》 | 模块常量 `DOSSIER_BOOK`/`STORY_BOOK` |
| `worldbookDataFiler.fileDataPatch` | 各设定书（武备/建筑等） | 按补丁 target 找条目所在书 |

后果：**同一张卡开两个聊天（两条剧情线），A 线诞生的机娘档案会写进 B 线也在读的同一本书**——跨聊天数据污染。剧情线越多、写入越活跃，污染越重；用户无法按聊天清理，也无法安全删除某条线的档案。

### 1.2 缺失的地基能力（本设计补齐）

1. **聊天身份读取**：当前聊天是谁（chatId/名字），什么时候切换了（CHAT_CHANGED）；
2. **聊天↔世界书绑定**：每聊天一本书的建立、读取、防漂移守卫；
3. **绑定管理面**：用户可见"当前聊天对应哪本书"，可改聊天名、可清理孤儿书（独立 UI 任务消费本地基）。

### 1.3 API 事实基座（已核验，置信度标注）

| 能力 | API | Surface | 置信度 |
| :--- | :--- | :--- | :--- |
| 读当前聊天绑定书 | `getChatWorldbookName('current')` → `string \| null` | Tavern Helper | 高（@types＋官方文档双源吻合） |
| 建/取聊天书 | `getOrCreateChatWorldbook('current', name?)` → `Promise<string>` | Tavern Helper | 高 |
| 重绑聊天书 | `rebindChatWorldbook('current', name)` | Tavern Helper | 高 |
| 读聊天 ID | `SillyTavern.getCurrentChatId()` → `string` | ST core（getContext） | 高 |
| 改聊天名 | `SillyTavern.renameChat(old, new)` | ST core | 高（拼写）/ 中（副作用） |
| 聊天元数据 | `chatMetadata` ＋ `saveMetadata()` | ST core | 高 |
| 切聊天事件 | `tavern_events.CHAT_CHANGED` | Tavern Helper 事件 | 高 |
| 书条目写入 | `updateWorldbookWith(name, updater)` | Tavern Helper | 高（girlFiler 已在用） |

⚠️ **两项真机必测**（文档未给保证，不得假定）：
1. `renameChat` 后聊天书绑定是否随迁（官方文档只说 checkpoint 链会断，未提世界书绑定）；
2. `getOrCreateChatWorldbook` 传入已存在书名时的行为（复用 or 报错）。

## 2. 第二章 · 绑定合同（Q2=A ＋ Q3=A · 冻结对象）

### 2.1 唯一真源：酒馆原生绑定

**聊天↔书的绑定关系只有一个真源＝酒馆自身的 chat worldbook 绑定**（`getOrCreateChatWorldbook` 建、`getChatWorldbookName` 读）。🔴 不自建 chatId→书名映射表、不做双真源同步（B4 缓存腐败旧雷教训：多一层缓存就多一个腐败面）。

### 2.2 命名合同（Q3=A：书名与聊天名解耦）

- 创建时使用规范名：**`红警档案·{角色名}·{短时间戳}`**（如 `红警档案·红警指挥系统·20260922T1530`）；短时间戳取创建时刻，保证同角色多聊天不撞名；
- 🔴 书名**不含聊天名**——聊天随便改名，书名不动、绑定不断（绑定由酒馆原生机制按聊天文件维持，不依赖名字匹配）；
- 管理页面显示「当前聊天 ⇆ 档案书名」对照，归属一眼可辨；
- `renameChat` 作为管理页可选操作提供，执行前必须警告「checkpoint 链会断」（官方文档明示），且改名后立即复验绑定仍在（§1.3 真机必测项 1 的运行时兜底）。

### 2.3 写前三重守卫（Q2=A · 🔴 红线协议）

一切经本地基的世界书写入，落笔前必须现场执行（不缓存、不跳步）：

```text
守卫① 聊天身份未漂移：写入发起时重取 SillyTavern.getCurrentChatId()，
        与本次写入事务开始时记录的 chatId 一致；不一致＝聊天已切换，拒写。
守卫② 绑定存在：getChatWorldbookName('current') 非 null；
        null＝本聊天尚无档案书（走 §3.1 建书流程或拒写，按调用方声明的意图）。
守卫③ 书实体存在：绑定书名 ∈ getWorldbookNames()；
        不在＝绑定悬空（书被外部删除），拒写并报孤儿绑定。
```

- 任一守卫失败 → **fail-closed**：拒绝写入＋结构化错误留痕（含失败守卫编号、期望值、实测值），UI 层截获展示；🔴 绝不静默降级写入全局书或其他聊天的书；
- 守卫协议实现为纯函数可测层（注入 API 读数）＋薄副作用层（真实调 API），对齐 girlFiler「渲染纯函数＋fileDossier 副作用」既有分层。

### 2.4 CHAT_CHANGED 生命周期

- 监听 `tavern_events.CHAT_CHANGED`：切聊天时丢弃一切内存态的"当前书名"临时值（本设计本就不缓存真源，此处只清理 UI 展示态）；
- 写入事务跨楼层挂起期间发生 CHAT_CHANGED → 该事务作废重验（守卫①天然拦截）；
- 对齐既有 `reloadOnChatChange` 先例（util/script.ts）。

## 3. 第三章 · 聊天档案书生命周期

### 3.1 建书时机：首次需要写入时惰性创建

- 不在聊天创建时预建（避免空书泛滥）；第一笔档案写入到来时若守卫②为 null，走 `getOrCreateChatWorldbook('current', 规范名)` 创建并绑定，然后重跑三重守卫再写；
- 创建即绑定为**聊天书**（chat-scoped），不占角色卡 primary/additional 位、不进全局启用列表——激活范围天然限定本聊天，这正是防污染的酒馆原生语义；
- 建书失败（API 不可用/宿主拒绝）→ fail-closed，写入挂起进暂存区（pending_lore 既有机制天然承接：入档失败不清暂存，下轮重试）。

### 3.2 书内结构

- 聊天档案书承载**本聊天线生长出的增量内容**；条目体例沿用 girlFiler 既有渲染格式（八段档案/人物条目/阵容总览），comment 定位 upsert 幂等语义不变；
- 全局共享书（《机娘·能力档案》《剧情·北坡纪事》装的**种子/设计态基线**内容，以及武备/建筑等设定书）保持只读共享——聊天线不再往里写（v1 迁移边界见 §4）。

### 3.3 删除与孤儿治理

- 删聊天不自动删书（酒馆不提供钩子且误删不可逆）——孤儿书（无聊天绑定指向的 `红警档案·*`）由管理页面列出，用户手动清理；
- 🔴 本地基不做任何自动删书；删除是驾驶员/用户在管理页的显式操作。

## 4. 第四章 · v1 迁移边界（Q4=B · girlFiler 双书先行）

### 4.1 v1 迁移：girlFiler

- `fileDossier` 的写入目标从常量双书改为**当前聊天档案书**（经三重守卫）；渲染纯函数（renderDossierContent/renderStoryContent/renderRosterLine）零改动，只换落点；
- 档案段与剧情段落入同一本聊天书（每聊天一本，Q3 用户好管理），以 comment 前缀（`档案·{名}·`/`剧情·{名}·`）区分段位，替代原双书分卷；阵容总览条目在聊天书内自建（首次写入时创建）；
- 既有全局双书中的**存量条目不迁移**（白凌等种子机娘属于设计态基线，继续全局共享）；v1 只改新写入的落点。

### 4.2 v1 不动区（🔴）

- `worldbookDataFiler`：改的是武备/建筑设定书的 `<数据>` 块，语义是**全局设定演化**而非聊天线档案——「全局 vs 聊天」归属须独立裁定，v1 零改动；
- `dlcInstaller`／`tavernRegexPipeline`／catalog 三级 Fallback 读链：零改动；
- `parsePipeline`／schema.ts：零改动（pending_lore 暂存机制原样复用）。

### 4.3 后续候选（Parking，须独立立项）

- worldbookDataFiler 补丁分流（全局设定 vs 聊天线改装的双轨裁决）；
- codex 索引的聊天维度镜像；
- 剧情事件流水（timeline）条目入聊天书。

## 5. 第五章 · 管理页面合同（独立 UI 任务消费）

管理页面（PanelSystem 或独立面板，实现归独立 UI 任务）至少呈现：

1. 当前聊天名＋chatId＋绑定档案书名（或「尚未创建」）；
2. 聊天改名入口（调 `renameChat`，前置 checkpoint 断链警告，改名后复验绑定）；
3. 本卡全部 `红警档案·*` 书列表＋孤儿标记（无绑定指向的书）；
4. 孤儿书手动删除（二次确认）；
5. 守卫失败留痕的最近记录（调试用）。

本设计只冻结以上信息合同，UI 形态归实现任务裁量。

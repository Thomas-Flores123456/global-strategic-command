# 动态档案引擎设计草案

> 状态：初步设计 / 待新会话继续收敛与实施
> 日期：2026-09-03
> 适用项目：SillyTavern 世界观构建 / 红警指挥系统
> 本文性质：机制草案与跨会话交接，不代表已完成实现，也不构成对世界书、catalog、MVU、动态科技数据库或真机的写入授权。

---

## 0. 一句话结论

建立一套统一的“动态档案引擎”，底层共享事务、版本、幂等、分支安全和按需注入能力，上层分别管理：

- NPC、机娘、建筑实例等动态实体档案；
- LLM 自创科技提案；
- 隐藏科技的发现/揭晓状态；
- 正式研究完成后产生的新解锁批次与科研通知。

> **私有结构化注册表保存机器真源；LLM 只提交受约束的字段级 Patch 或科技提案；代码负责确定性合并、科技树差集和可见性过滤；生成前只把本轮相关档案与回执注入 AI。**

不让 LLM 重写整篇旧档案，不让它自行猜科技树，不把全部 NPC 或全部科技正文塞进每轮可见的 `stat_data`，也不反复污染仓库中的静态世界书和 `catalog.ts`。

核心组合：

- 共用内核：稳定 ID、revision、eventId、消息页 pending、接受门、事务恢复；
- 实体更新入口：字段级 Patch；
- 科技更新入口：受约束提案、合法状态迁移或确定性研究完成事件；
- 更新执行：领域适配器 + 版本/幂等/Schema/权限校验；
- 展示输出：根据合并后的完整结构确定性重渲染（代码 cover 投影，而非 LLM cover 原文）；
- 科技解锁：代码比较研究完成前后的可研究集合，不由 LLM 推算；
- 读取控制：生成前选择相关实体、动态科技和未消费科研回执，只注入本轮需要的内容；
- 即时状态：继续由 MVU 管理；
- 长期档案：由私有动态注册表管理；
- 静态世界书与 base catalog：继续作为规则、类型、模板、开局基线和正式科技定义。

## 1. 背景问题

### 1.1 NPC

NPC 信息会随剧情持续变化，但全部放进常规 MVU 变量会导致：

- NPC 数量越多，每轮注入越大；
- 当前场景无关的 NPC 也被发送给模型；
- 缺少世界书式按关键词/场景激活；
- 聚合 NPC 与重要 NPC 的升级/拆分难以维护。

驾驶员的内容组织原则：

- 重要 NPC：独立人物条目；
- 不重要 NPC：按地点、组织或关系组成一个聚合条目；
- 不重要 NPC 若变得重要，应可从聚合条目晋升为独立条目。

### 1.2 机娘

机娘并非诞生后永远不变：

- 现代化改装会改变载具性能、武器或作战方式；
- 剧情成长可能形成新技能、长期缺陷或人格里程碑；
- 改装不产生新首台，人格与独一性保持连续；
- 不能让 LLM 用全文覆盖的方式更新档案，否则旧技能、人格或限制可能被漏掉。

### 1.3 建筑

建筑也有长期升级，尤其是 T2 超级武器向 T3 增强：

- 超时空传送仪 → 接入阵列/轨道中继；
- 天气控制仪 → 接入增强设施/聚变专线；
- 光棱塔 → 高功率与自主合束升级；
- 普通建筑也可能安装模块、形成永久损伤或独特特性。

建筑还必须区分：

- “天气控制仪”这一建筑类型能做什么；
- “北坡主基地一号天气控制仪”这个实例现在装了什么。

### 1.4 科技提案与研究解锁

动态科技存在两种性质完全不同的变化：

- **需要裁决的提案**：LLM 自创科技、隐藏科技正式揭晓等尚未进入当前存档的内容；
- **确定性的系统回执**：正式科技研究完成后，代码依据 catalog 前置关系计算出的新可研究项目。

前者允许驾驶员“已知晓并登记”或“封存并重试”；后者已经是科技树事实，只能确认已读或打开科研树，不能通过“封存”破坏前置闭环。

同时还要控制解锁扇出：一次研究完成可能使多条路线同时进入可研究状态，LLM 必须知道准确名单，但不应被迫读取每项科技的完整正文，玩家也不应连续收到十几个阻断弹窗。

### 1.5 分支与 swipe

AI 回复中的变化不能在生成结束时立即永久写入聊天级档案：

- 玩家可能 swipe 或 regenerate；
- 被换掉页面中的 NPC 死亡、关系变化或机娘改造不能残留；
- 持久更新必须绑定当前有效消息/当前 swipe，并经过接受门。

## 2. 设计目标与非目标

### 2.1 目标

1. NPC、机娘、建筑共用一套更新事务底盘。
2. 动态科技和隐藏科技复用同一事务内核，但保留独立领域适配器与状态机。
3. 不相关实体、不相关科技正文不进入本轮 prompt。
4. 未提及字段在更新后完整保留。
5. 同一更新事件或解锁批次重复处理不产生重复结果。
6. 标准科技改造尽量使用确定性配方，而不是让 LLM 发明结果。
7. 正式科技的新解锁项由代码计算集合差集，LLM 只负责叙述。
8. 大量新解锁科技合并成单个批次，完整名单紧凑告知、详细资料按需读取。
9. 隐藏科技在揭晓前不得泄露真名、答案，甚至不得泄露隐藏项数量。
10. swipe/regenerate 不污染已接受分支。
11. 现有世界书与 base catalog 大部分保持原样，不做全库重写。
12. 新功能可以分批落地，先解决最小闭环，再扩展领域和 UI。

### 2.2 非目标

1. 不把动态档案引擎做成无边界的通用数据库平台。
2. 不允许 LLM 直接操作任意 JSON Path。
3. 不让 LLM 输出文本级 `-旧句/+新句` diff。
4. 不以动态状态反写静态设计文档、base catalog 或基础世界书。
5. 不允许自创科技直接自动写入仓库 `catalog.ts`；正史化必须另走人工审阅链。
6. 不允许 LLM 一句话同时“创造、批准、研究完成”一项科技。
7. 不允许玩家封存已经由正式科技树确定性产生的普通后继解锁。
8. 不在本机制中处理短期 HP、当前弹药、冷却倒计时或研究 ETA 等即时值。
9. 不在第一版迁移全部旧人物/机娘条目。
10. 不在没有真机证据前依赖“阻断当前生成后无感续发”。

## 3. 真源与存储分层

本项目原有静态真源顺序继续保持：

```text
设计文档 → 静态世界书 → catalog → MVU
```

当前聊天的动态剧情与动态科技另开运行态支路，不反向污染静态链：

```text
已接受的剧情/改造事件
  → 私有动态注册表·实体域（机器真源）
  → 本轮按需渲染投影（AI 可见）
  → MVU 即时状态（短期值）

已批准的自创科技 / 已揭晓隐藏科技状态
  → 私有动态注册表·科技域（当前存档 overlay）
  → effective catalog = base + 正式 DLC + 当前存档 overlay
  → 定义进入动态档案，研究项目进度/ETA 留在 MVU queue

正式研究完成事件
  → 代码提交 tech.done
  → 比较提交前后的可研究集合
  → 生成有界的 ResearchUnlockBatch
  → UI 通知 + 下一次生成的紧凑科研回执
```

### 3.1 静态世界书

负责：

- 世界规则；
- 科技、建筑、武备类型定义；
- 型号能力模板；
- 首台人格方向模板；
- 开局人物与剧情基线；
- 标准升级路径及其理论上限。

原则：**不写“当前存档中的某个实例已经升级”**。

### 3.2 私有动态注册表

这是运行态机器真源的逻辑总称，覆盖实体域与动态科技域；它们共享 revision、eventId 幂等、分支接受门、事务恢复和按需投影规则，但保留各自的 Schema 与领域适配器，不把科技强行建模为实体。

候选载体是聊天作用域私有变量。物理实现可拆分为 `$entity_registry` 与独立的动态科技注册表，也可由一个总容器分域保存；最终命名与拆分方式待实施会话拍板。

实体域负责：

- 稳定实体 ID；
- 当前长期档案；
- 静态基线引用；
- 重大长期变化与必要审计信息。

科技域负责：

- 已批准的自创科技定义；
- 已揭晓隐藏科技的运行态阶段；
- 当前存档的 effective catalog overlay；
- 科研裁决、解锁批次与必要审计引用。

两个域共同保存 revision 与已应用 eventId。私有动态注册表不应被“当前战局注入”整体发送给模型；只允许选择器读取本轮相关记录并渲染有界投影。需要确认现有注入路径只读取 `stat_data`，并为私有动态注册表补充自动测试与真机证据。

### 3.3 MVU `stat_data`

负责短期和即时状态：

- 当前地点、职务、HP；
- 建筑运转/停机/受损；
- 当前弹药、剩余冷却、队列进度；
- 当前场景实体 ID；
- 本轮任务相关实体 ID。

建议只保留小型选择索引，例如：

```yaml
scene_entities:
  - G:beipo:bailing
  - NPC:yunxi:shopkeeper-zhou
  - B:beipo:weather-01
```

### 3.4 AI 可见动态投影

生成前，根据当前场景和用户输入选择少量实体，将其结构化档案渲染为散文投影后注入。

这是运行时的“按需可见层”，不是机器真源。

### 3.5 Chat Lorebook 的定位：可选投影/导出，而非首版硬依赖

早期方案曾考虑把动态正文持续写入 Chat Lorebook，再用机器 key 激活。该方案仍可作为：

- 可视化浏览载体；
- 导出/审计载体；
- 运行态投影缓存；
- 宿主版本与分支同步经真机证明后的增强路线。

但它不宜在第一版直接成为唯一机器真源，原因是：

- swipe 后同一本 Chat Lorebook 可能暂时保留旧分支投影；
- 世界书写入为异步副作用，生成前是否能等待完成必须真机验证；
- 动态书缓存失配时，当前 prompt 可能读到旧状态。

第一版更稳妥的候选是：**私有注册表存真源，生成前直接注入已选择实体的当前渲染投影。**

## 4. 领域分类模型

动态档案引擎不把所有对象强塞进同一个 `EntityKind`。底层可抽象为 `DynamicRecordKernel`，上层使用领域适配器：

```ts
DynamicRecordKernel
  ├─ NpcAdapter
  ├─ GirlAdapter
  ├─ BuildingAdapter
  ├─ DynamicResearchAdapter
  └─ HiddenResearchAdapter
```

它们共享稳定 ID、revision、eventId、pending、接受门、审计、恢复与按需注入；字段白名单、状态机、渲染模板和权限规则则由各适配器独立定义。

### 4.1 实体类型 `kind`

首批：

```ts
type EntityKind = 'npc' | 'girl' | 'building';
```

未来可扩：

```ts
'vehicle' | 'equipment' | 'base' | 'organization'
```

### 4.2 实体层级 `level`

```ts
type EntityLevel =
  | 'archetype' // 类型：天气控制仪、F-16C、网络战中心
  | 'template'  // 模板：首台人格方向、型号技能简档
  | 'instance'  // 实例：白凌、周掌柜、北坡一号天气控制仪
  | 'group';    // 聚合组：沈氏医堂雇员、云溪镇东市商户
```

### 4.3 稳定 ID

示例：

```text
G:beipo:bailing
NPC:yunxi:shopkeeper-zhou
NPCG:yunxi:east-market
BUILDING_TYPE:weather-control
B:beipo:weather-01
```

要求：

- ID 不随化名、显示名或世界书 comment 变化；
- 更新和幂等均按 ID，不按自然语言名称；
- 人类名称/化名只是触发别名；
- 类型与实例不得共用 ID。

### 4.4 通用注册项草案

```ts
interface EntityRecord {
  id: string;
  kind: EntityKind;
  level: EntityLevel;
  name: string;
  aliases: string[];

  archetypeId?: string;
  groupId?: string;
  baseRefs: Array<{
    book: string;
    uid?: number;
    name?: string;
    contentHash?: string;
  }>;

  revision: number;
  appliedEventIds: string[];
  updatedAt: string;

  profile: NpcProfile | GirlProfile | BuildingProfile | GroupProfile;
}
```

`appliedEventIds` 不应无限增长。可采用：

- 最近 N 条 + 历史摘要；或
- 有界哈希集合；或
- 以消息 ID/swipe ID 派生的事件号并定期 checkpoint。

具体策略待实现会话做容量估算。

## 5. 通用更新协议

### 5.1 核心思想

> **Patch 进入，确定性合并，投影 cover 输出。**

- LLM 不生成整篇新档案；
- LLM 不生成文本 diff；
- LLM 只说明“哪个语义字段发生了什么变化，以及该字段现在是什么”；
- 代码保留未提及字段；
- 合并后由渲染器重新生成当前投影。

### 5.2 通用事件草案

```ts
interface EntityPatch {
  eventId: string;
  entityId: string;
  entityKind: EntityKind;
  scope: 'instance' | 'group' | 'archetype';
  baseRevision: number;
  source: 'catalog_recipe' | 'narrative' | 'driver';
  reason: string;
  operations: TypedOperation[];
}
```

禁止 LLM 提交任意 JSON Pointer。操作必须通过适配器白名单，例如：

```ts
type TypedOperation =
  | { field: 'personality_summary'; op: 'replace'; value: string }
  | { field: 'milestones'; op: 'append'; key: string; value: string }
  | { field: 'skills'; op: 'upsert'; key: string; value: SkillRecord }
  | { field: 'skills'; op: 'remove'; key: string; reason: string }
  | { field: 'retrofits'; op: 'upsert'; key: string; value: RetrofitRecord };
```

### 5.3 操作语义

| 操作 | 适用 | 说明 |
|---|---|---|
| `replace` | 单段字段 | 只覆盖该字段，不碰其他字段 |
| `upsert` | 命名技能、模块、关系、履历 | 按稳定 key 新增或替换 |
| `append` | 重大事件/里程碑 | 幂等追加，有长度上限 |
| `remove` | 技能移除、模块拆除 | 高风险，默认需要确认或确定性配方 |
| `archive` | NPC 离场、建筑摧毁 | 保留历史，不再参与默认选择 |
| `promote` | 聚合 NPC 晋升独立条目 | 事务操作，必须同时从组中移除 |

### 5.4 版本与冲突

每次应用前检查：

1. `eventId` 是否已应用；
2. `baseRevision` 是否等于当前 revision；
3. `entityKind` 和字段适配器是否匹配；
4. 目标字段是否允许该操作；
5. Schema 验证是否通过。

冲突时不得静默覆盖，应进入：

- 自动重基（仅低风险、可证明不冲突）；或
- 系统面板人工确认；或
- 隔离区等待修复。

## 6. 类型适配器

通用协议只处理事务，不把不同实体强行塞成同一种字段。

### 6.1 NPC 适配器

长期字段候选：

```ts
interface NpcProfile {
  identity: string;
  appearance: string;
  personality: string;
  relationships: Record<string, RelationshipRecord>;
  longTermGoals: string[];
  knownFacts: string[];
  longTermStatus: string;
  majorEvents: EventSummary[];
  importance: 'minor' | 'major' | 'core';
}
```

不进入长期档案：临时所在位置、短期伤势、一次性情绪、当前动作。

聚合 NPC 规则：

- 小人物按地点/组织入 `group`；
- 每名成员仍有稳定 ID；
- 更新只改成员，不 cover 整组；
- 成员变重要时执行 `promote`：建立独立实例、从组正文及触发别名中移除、保留历史引用；
- 避免独立条目和聚合条目同时注入同一人的重复正文。

### 6.2 机娘适配器

长期字段候选：

```ts
interface GirlProfile {
  model: string;
  identity: string;
  appearance: string;
  personality: string;
  formMechanism: string;
  skills: Record<string, SkillRecord>;
  weapons: Record<'primary' | 'secondary' | 'trump', WeaponRecord>;
  structuralFlaws: Record<string, string>;
  exposureProfile: string;
  balancePosition: string;
  retrofits: Record<string, RetrofitRecord>;
  milestones: EventSummary[];
}
```

更新规则：

- 姓名、型号、首台身份默认不可由普通 narrative patch 修改；
- 技能按技能名 upsert，不整段重写全部技能；
- 武器按主/副/底牌槽位更新；
- 现代化改装不产生新首台；
- 人格核心默认保留，成长以里程碑或受控段落更新；
- 删除技能、改变核心人格、改变独一性属于高风险操作。

### 6.3 建筑适配器

长期字段候选：

```ts
interface BuildingProfile {
  archetypeId: string;
  baseId: string;
  displayName: string;
  installedUpgrades: Record<string, UpgradeRecord>;
  modules: Record<string, ModuleRecord>;
  permanentTraits: Record<string, string>;
  permanentDamage: Record<string, string>;
  longTermConfiguration: string;
  history: EventSummary[];
}
```

类型与实例必须分开：

```text
BUILDING_TYPE:weather-control
  = 天气控制仪类型、标准能力、理论升级路径

B:beipo:weather-01
  = 北坡一号天气控制仪、实际安装升级与永久变化
```

即时状态仍由 MVU 管：

- 当前停机；
- 当前耗电；
- 当前冷却；
- 当前受损；
- 建造/维修进度。

长期档案管理：

- 已安装升级；
- 永久模块；
- 长期配置；
- 永久结构缺陷；
- 独特事故遗留。

## 7. 动态科技、研究解锁与确定性改造

### 7.1 标准科技改造：确定性配方优先

对 catalog/设计中已明确定义的改造，不应让 LLM 决定结果。

配方草案：

```ts
interface RetrofitRecipe {
  id: string;
  targetKind: 'girl' | 'building';
  targetArchetype: string;
  policy: 'retrofit-existing' | 'module-per-instance' | 'doctrine-global';
  requiredResearch: string[];
  requiredBuildings?: string[];
  operations: TypedOperation[];
}
```

三种政策：

1. `retrofit-existing`：旧实例逐个付费改造；
2. `module-per-instance`：模块安装/拆除；
3. `doctrine-global`：研究完成后全局生效（谨慎使用）。

建议流程：

```text
研究完成
  → 解锁改造项目（不自动完成实例升级）
  → 玩家选择实例、支付费用并进入队列
  → 改造完成事件产生
  → 代码应用确定性 recipe
  → LLM 负责叙事表现，不负责发明结果
```

超级武器和现代化载具改造通常采用前两种，而非全局自动升级。

### 7.2 动态科技与隐藏科技记录

科技复用动态档案内核，但不属于 NPC/机娘/建筑的 `EntityKind`。

LLM 自创科技使用独立生命周期：

```ts
type DynamicResearchStatus =
  | 'proposal'
  | 'approved'
  | 'researching'
  | 'completed'
  | 'rejected';

interface DynamicResearchRecord {
  id: string;
  status: DynamicResearchStatus;
  revision: number;
  appliedEventIds: string[];

  name: string;
  tier: number;
  line: string;
  cost: number;
  durationDays: number;
  prerequisites: string[];
  unlocks: string[];
  limits: string[];
  exposure: string[];
  narrativeBasis: string;
}
```

流程必须是：

```text
LLM 提案
  → 名称/近名/前置/时代/层级/解锁物/工程代价校验
  → 驾驶员裁决
  → 批准后写入当前存档 dynamic catalog overlay
  → 进入正常研究队列
  → 研究完成后才成为 completed
```

不得一句话同时“创造、批准并完成”一项科技；不得自动反写仓库 `catalog.ts`。优秀动态科技若要正史化，另走：

```text
导出审阅包 → 驾驶员批准 → 设计文档 → 世界书 → catalog
```

隐藏科技使用阶段可见性状态机：

```ts
type HiddenResearchPhase = 0 | 1 | 2 | 3 | 4;

interface HiddenResearchState {
  researchId: string;
  phase: HiddenResearchPhase;
  revision: number;
  acceptedClueIds: string[];
  questIds?: string[];
}
```

阶段含义：

| phase | 对玩家/LLM 可见内容 |
|---:|---|
| 0 | 未发现；真名、答案、用途和数量全部不可见 |
| 1 | 只允许模糊异常方向 |
| 2 | 调查代号、合法线索和调查任务 |
| 3 | 正式揭晓；真名可见并可按规则进入可研究集合 |
| 4 | 已完成 |

隐藏科技完整定义仍由隐藏 DLC 内部权威注册；运行态只保存阶段和已接受线索。自创科技审查若碰撞未揭晓隐藏名池，只返回“与受保护研究方向冲突”等中性结果，不泄露命中对象。

### 7.3 正式研究完成后的解锁差集

普通后继科技不是 LLM 提案，而是正式 catalog 前置条件刚刚满足的系统事实。代码必须在提交研究完成事件前后分别计算当前可研究集合：

```ts
const before = deriveResearchable(stateBefore, effectiveCatalog);
const after = deriveResearchable(stateAfter, effectiveCatalog);

const newlyResearchable = difference(after, before);
```

此处为概念代码，实际调用签名以实施时的 `catalog.ts`/派生器为准。

建议形成统一变化对象：

```ts
interface ResearchTransition {
  newlyCompleted: string[];
  newlyResearchable: string[];
  newlyVisible: string[];
  stillBlocked: string[];
}
```

口径：

- `newlyCompleted`：本事务真正提交完成的研究；
- `newlyResearchable`：提交后首次满足全部条件的研究；
- `newlyVisible`：可见性状态合法提升的研究，不等同于可研究；
- `stillBlocked`：仍缺其他前置，只用于系统诊断，不能向玩家宣称已解锁；
- 已经处于可研究状态的项目不重复通知；
- LLM 不参与集合计算，也无权添加或删减计算结果。

### 7.4 科研解锁批次

一次研究完成可能同时打开多条路线，应合并为一个幂等批次：

```ts
interface ResearchUnlockBatch {
  batchId: string;
  causedBy: string[];
  committedRevision: number;
  createdAt: string;

  newlyResearchable: Array<{
    researchId: string;
    name: string;
    line: string;
    tier: number;
    reason: string;
    priority: 'focus' | 'normal';
  }>;

  playerAcknowledged: boolean;
  narrativeAcknowledged: boolean;
  status: 'queued' | 'shown' | 'consumed' | 'superseded';
}
```

`batchId` 应由完成事件、有效目录 revision 和结果集合确定性派生，例如：

```text
unlock:<completion-event-id>:<catalog-revision>:<result-hash>
```

这样页面刷新、多 iframe 重载、重复结算或失败重试都不会重复制造通知。

`playerAcknowledged` 与 `narrativeAcknowledged` 必须分开：

- 玩家点“已知晓”只代表 UI 已读；
- LLM 实际收到并叙述过回执后，才标记叙事已消费；
- 任一状态未完成时，可在通知中心或生成前注入队列中继续保留，但不重复阻断玩家。

### 7.5 让 LLM 知道什么

LLM 必须知道**全部新解锁项目的准确名称和 ID**，但不需要同时读入每项科技的完整档案。

第一层注入全部紧凑名单：

```xml
<科研解锁回执 batch_id="unlock:advanced-avionics:rev-42">
完成研究：先进航电工学
新进入“可研究”状态，共 7 项：
- R:AIR:NEXT-AIR｜下代制空工学｜空军 T2
- R:AIR:AEW-C2｜空中预警指控工学｜空军 T2
- R:ALLIED:NETWORK｜盟军联合作战链路｜盟军特色 T2
……
口径：以上项目只是现在可以开始研究，不是已经掌握；不得替玩家自动选择下一项研究。
</科研解锁回执>
```

第二层只展开 3～5 项重点摘要。重点项由代码排序，不让 LLM 自选遗漏：

1. 玩家已钉选的科研路线；
2. 刚完成科技的直接后继；
3. 新开启的科技路线；
4. 与当前战略需求或任务直接相关；
5. 本轮合法揭晓的隐藏科技。

剩余项目只需按路线概括，完整价格、周期、前置、解锁物和限制由科研面板从 effective catalog 按需读取。

普通剧情不重复发送当前全部可研究目录。只有用户明确询问“现在能研究什么”等科研查询时，才临时注入完整可研究清单及必要参数。

### 7.6 两类前端卡片

科技 UI 共用弹窗、pending、消息页绑定和审计底盘，但业务语义分为两类。

#### A. 决策卡

适用：

- LLM 自创科技提案；
- 隐藏科技正式发现/揭晓且对应叙事尚未接受；
- 其他尚未正式进入当前存档的动态科技。

按钮：

```text
[已知晓并登记] [封存并重试]
```

“已知晓并登记”执行领域校验，并将动态科技写入当前存档 overlay，或提交隐藏科技合法阶段迁移；“封存并重试”拒绝提案，并把绑定消息页的整段叙事标记为非正史，再创建新的 swipe。

#### B. 系统回执卡

适用：

- 正式研究完成；
- 由代码确定性计算出的普通后继解锁；
- 已批准动态科技完成后产生的正常后继解锁。

按钮：

```text
[已知晓] [打开科研树] [稍后查看]
```

不得出现“封存”。研究完成和普通后继解锁已经是系统状态；玩家只能确认已读、查看详情或延后处理，不能破坏科技树一致性。

### 7.7 大量解锁的折叠与通知节流

一次完成事件只生成一个批次弹窗，禁止逐项轰炸玩家：

| 新解锁数量 | 默认展示 |
|---:|---|
| 1～4 | 全部展开 |
| 5～8 | 展开重点 3 项，其余折叠 |
| 9 及以上 | 按科研路线分组，只展示重点项和各组数量 |

建议 UI：

```text
研究完成：先进航电工学
新增可研究项目：12

推荐关注
1. 下代制空工学
2. 空中预警指控工学
3. 盟军联合作战链路

空军线 +5｜盟军特色线 +3｜航天工业线 +4
[已知晓] [打开科研树] [稍后查看]
```

节流规则：

- 每个已接受回合最多显示一个阻断式科研通知；
- 其余批次进入通知中心，按 `createdAt` 和战略优先级排序；
- 多项研究同一结算点完成时，可合并为一个批次，`causedBy` 保存全部来源；
- 同一 `researchId` 在批次内去重；
- 同一状态迁移只通知第一次；
- 页面重载不重复弹已经 `playerAcknowledged=true` 的批次；
- catalog 静态校验对“单一科技直接扇出超过 8 项”给出设计警告，但不必一律报错。

### 7.8 隐藏科技的通知过滤

`ResearchTransition` 进入 UI 或 prompt 前必须经过 `HiddenResearchAdapter` 过滤：

- phase 0：项目完全移除，连“另有 N 项隐藏科技”都不允许出现；
- phase 1：只允许“捕捉到一个异常研究方向”等模糊描述；
- phase 2：只显示调查代号、已接受线索和合法任务；
- phase 3：真名和正式研究信息才可进入新揭晓/可研究列表；
- phase 4：可显示已完成。

如果普通研究完成仅使隐藏项目从 phase 0 进入 phase 1，LLM 最多收到：

```text
情报部门捕捉到一个新的异常研究方向；不得给出正式名称、最终用途、完整前置或解锁答案。
```

### 7.9 完成来源与分支安全

研究完成事件可能来自两条路径：

#### 系统队列确定性结算

```text
研究队列到期
  → 系统提交 tech.done
  → 计算解锁差集
  → 创建 ResearchUnlockBatch
  → UI 展示并在下一次生成注入回执
```

研究事实已经提交。之后若玩家 swipe “科研人员庆祝”的叙事，只重写表现，不回滚研究状态；新页面继续收到同一未消费回执，直到一个页面被接受并完成叙事消费。

#### AI 回复中的完成提案

```text
AI 声称研究完成
  → 形成绑定 message_id + swipe_id + message_hash 的 pending completion
  → 玩家下一次 normal 发送，视为接受当前页
  → 正式提交 tech.done
  → 计算解锁差集
  → 创建批次并注入本轮生成
```

如果当前页被封存或 swipe 掉：

- pending completion 作废；
- 不写 `tech.done`；
- 不计算后继解锁；
- 不弹科研回执。

若生成前异步事件不能保证等待持久化，首版应采用“同步内存提交有效快照 + 本轮直接注入回执 + 后台持久化并显式失败”的候选方案，最终仍以 Phase 0 真机时序探针为准。

## 8. 生成前按需读取

### 8.1 选取来源

本轮实体候选来自：

1. `scene_entities`：当前在场；
2. 用户输入显式点名/化名；
3. 当前任务绑定人物；
4. 当前基地绑定建筑；
5. 上一轮必要黏性实体；
6. 驾驶员手动固定。

建议按预算与优先级裁剪：

```text
当前交互对象 > 用户显式点名 > 当前任务核心 > 当前场景重要实体 > 聚合组 > 低优先级旁观者
```

第一版可设置硬上限，例如：

- 重要人物 3 名；
- 次要人物组 1 组；
- 相关建筑实例 2 座；
- 超限时面板显示“本轮裁剪了哪些实体”。

具体上限须通过真实 prompt token 统计调整。

### 8.2 推荐热路径：直接注入当前投影

候选方案：在 `tavern_events.GENERATION_AFTER_COMMANDS` 阶段：

1. 同步读取已准备好的当前有效注册表快照；
2. 选择本轮实体；
3. 确定性渲染少量投影；
4. 用 `injectPrompts` 注入。

概念形态：

```ts
injectPrompts(
  [{
    id: 'eva-entity-projection',
    position: 'in_chat',
    depth: 0,
    role: 'system',
    content: renderedProjection,
    should_scan: true,
  }],
  { once: true },
);
```

`should_scan: true` 可让动态投影中的类型名继续触发静态世界书，例如：

- 动态投影写“北坡一号天气控制仪”；
- 静态世界书按“天气控制仪”提供类型能力与升级路径。

注意：depth/role/顺序最终必须结合项目真实预设与 Prompt Manager 验证，不能照抄示例即施工。

### 8.3 备选增强：隐形机器 token 激活 Chat Lorebook

如果真机证明 Chat Lorebook 缓存与分支同步稳定，可为动态条目使用：

```text
@ENTITY:G:beipo:bailing
@ENTITY:B:beipo:weather-01
```

并在生成前：

```ts
injectPrompts(
  [{
    id: 'eva-entity-scan-keys',
    position: 'none',
    depth: 0,
    role: 'system',
    content: '@ENTITY:G:beipo:bailing @ENTITY:B:beipo:weather-01',
    should_scan: true,
  }],
  { once: true },
);
```

静态声明说明：

- `position: 'none'` 不把 token 本身发给 AI；
- `should_scan: true` 让 token 参与世界书扫描；
- `once: true` 只用于下一次生成；
- `injectPrompts` 文档建议可在 `GENERATION_AFTER_COMMANDS` 中注入。

这些只是本地声明/文档证据。事件是否等待异步 listener、dry run 是否消耗 once、不同生成类型的执行顺序，仍须真机验证。

### 8.4 不推荐首版采用“阻断生成后续发”

原因：

- 当前事件签名未提供明确的暂停/恢复令牌；
- `stopGeneration` 后重发容易造成双生成、swipe 异常和并发污染；
- 生成前选择和渲染若已在内存准备好，无需阻断；
- 若更新提交需要异步等待，应优先设计接受门和同步快照，而不是伪装成同一请求续发。

## 9. 分支安全、接受门与科技裁决

### 9.1 基本规则

AI 新回复只产生“提案”，不立即成为聊天级长期真源。

候选流程：

```text
AI 回复生成
  → 解析 <实体档案>/<实体更新>
  → 按 message_id + swipe_id + message_hash 存入消息级 pending
  → 玩家下一次正常发送消息
  → 当前活动 swipe 视为接受
  → 应用 pending 到聊天级注册表
  → 本轮使用合并后的有效投影
```

### 9.2 不自动接受的生成类型

默认：

- swipe；
- regenerate；
- continue；
- quiet；
- prompt dry run。

它们如何继承/提交必须逐类真机验证后定稿。

### 9.3 消息级 pending 建议字段

```ts
interface PendingEntityEvents {
  messageId: number;
  swipeId: number;
  messageHash: string;
  events: EntityPatch[];
  renderedPreview: string;
  status: 'pending' | 'accepted' | 'rejected' | 'conflict';
}
```

### 9.4 异步提交时序的关键悬案

必须验证：

1. `GENERATION_AFTER_COMMANDS` 是否等待 async listener；
2. `updateVariablesWith`/世界书写入是否能在 prompt 构建前完成；
3. 若不能等待，是否采用“同步内存合并 + 本轮直接注入新投影 + 后台持久化”；
4. 后台持久化失败时，如何阻止下一轮继续建立在未落盘状态上。

首版应把失败显式显示在系统面板，不得静默吞掉。

### 9.5 “封存并重试”的消息页事务

“封存”不是普通删除按钮，而是同时处理科技提案和绑定叙事分支的高风险事务。弹窗打开时必须固化：

```ts
interface ProposalDecisionBinding {
  chatId: string;
  messageId: number;
  swipeId: number;
  messageHash: string;
  proposalId: string;
  eventId: string;
}
```

二次确认文案必须明确：

> 封存后，该科技不会写入当前存档；当前消息页对应的整段叙事将被视为非正史，并从上一条用户消息重新生成。是否继续？

确认后的候选事务：

1. 获取跨 iframe 的单实例事务锁，防止双击和并发裁决；
2. 重读当前 `chatId/messageId/swipeId/messageHash`，任一不一致即拒绝执行；
3. 将提案从 `proposal` 原子转为 `rejected/sealed`；
4. 写入 `proposalId/eventId` 拒绝墓碑，使生成前注入器立即排除它；
5. 不写动态科技数据库，不提交该页携带的研究完成或实体更新 pending；
6. 调用 SillyTavern 原生高层 fresh-swipe 流程，从上一条用户消息重新生成；
7. 生成后重读该楼全部 swipes，确认确实新增非空页面；
8. 记录被拒分支与替代分支的 message/swipe/hash；
9. 释放锁并写 UI 回执。

推荐由窄宿主适配器调用目标版本提供的高层 `context.swipe.to`。概念形态：

```ts
await host.swipeFresh({
  messageId,
  expectedSwipeId: binding.swipeId,
  targetSwipeId: before.swipes.length,
});
```

适配器内部在 SillyTavern 1.18.0 可映射到：

```ts
await context.swipe.to(null, 'right', {
  message: context.chat[messageId],
  forceMesId: messageId,
  forceSwipeId: before.swipes.length,
  repeated: false,
});
```

上述代码只记录目标安装源码证明过的调用方向，施工时仍须做 `typeof context.swipe?.to === 'function'`、当前聊天、最新 AI 楼、非生成中和消息页身份探针。

`/swipe direction=right await=true` 可作为兼容降级，但仅当当前已经是最后一个 swipe；否则它可能只切换已有页。最终 DOM 兜底为本机 1.18.0 的 `.last_mes .swipe_right`，同样只能在最后一页使用，并必须做生成后的数据核验，不能把 click 成功当成生成成功。

明确不采用：

- `setChatMessages([{ swipe_id }])`：只切换/改写已有消息页；
- 酒馆助手 `generate()`：返回文本，不自动挂载正常聊天 swipe；
- `sendGenerationRequest()`：底层供应商请求，不管理聊天、swipe、保存和事件；
- 裸 `Generate('swipe')`：缺少高层 swipe 预建槽位、UI 状态和失败回滚；
- `/regenerate`：会替换最后回复，群聊还有额外批次语义，不满足保留审计分支的默认策略。

后置成功条件至少包括：

```ts
after.swipes.length > before.swipes.length
  && after.swipe_id >= before.swipes.length
  && !['', '...'].includes(after.swipes[after.swipe_id].trim())
  && currentChatId === binding.chatId
```

`MESSAGE_SWIPED` 不能作为生成成功信号。目标源码中该事件发生在 `Generate('swipe')` 之前；最终必须以 `getChatMessages(messageId, { include_swipes: true })` 的读回结果和新页 hash 为准。

首版采用**逻辑封存**而非立即物理删除旧 swipe：

- 旧页保留为非当前页，便于审计；
- 拒绝墓碑阻止其重新登记科技；
- 用户若手动切回封存页，面板显示警告并禁止“已知晓并登记”；
- 暂不冒险删除可能与 `swipes/swipe_info/variables` 对齐相关的消息页数据。

如果新页生成失败：

- 提案仍保持 sealed，不恢复为可接受；
- 不写科技数据库；
- 显示“封存已生效，但重试生成失败”；
- 提供再次重试；
- 在出现通过后置核验的新页之前，不提交该楼层任何长期变化。

## 12. 提示词协议草案

### 12.1 新建实体

可以保留专用标签，降低一次性字段复杂度：

```xml
<实体档案>
- 实体类型: NPC
  名称: 周掌柜
  重要度: 次要
  身份: >-
    ……
  外观: >-
    ……
  性格: >-
    ……
</实体档案>
```

机娘仍可沿用 `<机娘档案>`，由解析层归一为通用实体创建事件。

### 12.2 更新实体

```xml
<实体更新>
- 事件ID: narrative:message-42:swipe-0:zhou-relation
  实体: 周掌柜
  实体类型: NPC
  基线版本: 3
  原因: 与指挥官完成药材交易后态度转变
  变更:
    - 字段: 关系
      操作: 替换
      键: 指挥官
      现行描述: >-
        从单纯警惕转为谨慎合作，仍不愿透露上游货源。
</实体更新>
```

提示词原则：

- 字段内用详实自然语言，不堆标签词；
- 只写正文中确实发生的长期变化；
- 未变化字段不输出；
- 短期动作、受伤、冷却不写入长期档案；
- 标准改造结果由系统配方产生，不要求 LLM 重复发明。

事件 ID 最好由代码根据消息和 swipe 生成，不让 LLM 自由命名；上例仅展示语义。

## 13. 自动/确认策略

| 变更 | 建议策略 |
|---|---|
| 新普通 NPC 建档 | 自动或批量入组 |
| 普通关系小幅变化 | 自动，但下一次正常发送时接受 |
| 新机娘首次建档 | 默认自动，保留系统面板开关 |
| catalog 标准改造 | 队列完成后确定性自动应用 |
| 新技能/长期缺陷 | 自动提案，可在面板复核 |
| 删除技能/人格重写 | 必须确认 |
| 修改型号/首台身份/独一性 | 必须确认 |
| 建筑实例永久升级 | 标准配方自动；叙事自创升级需确认 |
| NPC 死亡/叛变/阵营变化 | 高风险确认或下一轮接受门明确提示 |
| LLM 自创科技提案 | 决策卡：已知晓并登记 / 封存并重试 |
| 隐藏科技正式揭晓 | 通过合法 phase 迁移后使用决策卡；未揭晓信息继续隔离 |
| 正式研究完成 | 确定性自动提交，生成系统回执卡 |
| 普通后继科技进入可研究 | 代码差集自动登记；不可封存 |
| 大批新解锁科技 | 单批合并、分组折叠，其余进入通知中心 |

## 14. 系统面板建议

系统面板建议分为“动态实体”和“科研通知/提案”两个视觉分区，共用底层回执和事务状态。

“动态实体”区域：

- 本轮将注入哪些实体；
- 当前 token 估算；
- 待接受事件；
- 冲突/失败事件；
- 自动更新开关；
- 高风险确认；
- 查看实体 revision 与履历；
- 聚合 NPC 晋升按钮；
- 手动固定/取消本轮实体；
- 导出当前注册表/动态投影；
- 重建动态世界书缓存（若采用 Chat Lorebook 增强路线）。

“科研通知/提案”区域：

- 待裁决的动态科技与隐藏科技揭晓提案；
- 决策卡的绑定 `messageId/swipeId/hash`；
- 待显示、已显示、已读和已叙事消费的解锁批次；
- 按路线分组的新可研究项目；
- “打开科研树”定位；
- 被封存分支与替代 swipe 的审计记录；
- 生成失败后的再次重试；
- 当前回合被节流到通知中心的批次数量；
- 单次解锁扇出警告。

不得用 UI 的“看似成功”替代写后读回核验。

## 15. 事务与恢复

建议原子步骤：

1. 读取当前记录和 revision；
2. eventId 幂等检查；
3. 在内存副本应用 typed patch；
4. 适配器 Schema 校验；
5. 确定性渲染新投影；
6. 持久化私有注册表；
7. 读回核验 revision/hash；
8. 更新可选 Chat Lorebook 投影；
9. 读回核验世界书条目；
10. 标记 pending accepted；
11. 写回执。

若步骤 8 失败：

- 注册表仍为机器真源；
- 标记投影缓存 stale；
- 下一轮优先直接注入注册表渲染结果；
- 面板提供重建缓存，不把缓存失败误当注册表丢失。

如果要求真正跨两个存储原子提交，则需设计补偿事务；首版可以采用“注册表权威、投影可重建”的单向恢复模型，降低复杂度。

已核验符号与行为：

- `tavern_events.GENERATION_AFTER_COMMANDS(type, option, dry_run)`；
- `injectPrompts(prompts, { once })`；
- `InjectionPrompt.position: 'in_chat' | 'none'`；
- `InjectionPrompt.should_scan?: boolean`；
- `position:'none'` 的声明说明为“不发给 AI，但可用于激活世界书”；
- `stopGenerationById` / `stopAllGeneration` 存在，但不等于有可靠的暂停/恢复原请求语义；
- `setChatMessages` 可读取/修改/切换 swipes，但不会请求新的正常聊天生成；
- 酒馆助手 `generate()` 返回文本或工具调用结果，不自动挂载聊天 swipe；
- SillyTavern 1.18.0 的稳定上下文暴露 `swipe.to/left/right/state/isAllowed`；
- 高层 swipe 越过最后一页时建立新槽位、发出 `MESSAGE_SWIPED`，随后调用 `Generate('swipe')`；
- `Generate('swipe')` 构建上下文时移除当前 AI 回复，因此适合否定当前整段叙事后重试；
- `/swipe direction=right await=true` 会等待动作，但当前页右侧已有 swipe 时只切页；
- 当前 DOM 兜底选择器为 `.last_mes .swipe_right`；
- Chat Lorebook 仍为版本与分支一致性相关的候选增强能力。

## 20. 风险与待拍板问题

1. **机器真源载体**：聊天私有变量、消息级 checkpoint，还是两者混合？
2. **分支模型**：聊天级 registry + 消息 pending，还是每个有效 AI 楼保留私有 registry checkpoint？
3. **热路径**：直接注入动态投影，还是 Chat Lorebook + 隐形 key？
4. **事件时序**：生成前 hook 是否允许 await 持久化？
5. **自动接受边界**：下一次 normal 发送是否一律代表接受上一楼？
6. **高风险操作**：哪些必须驾驶员确认？
7. **NPC 晋升规则**：按出场次数、任务绑定还是手动决定？
8. **历史长度**：人物重大事件、改造履历各保留多少条？
9. **token 预算**：单实体/单轮上限与裁剪优先级；
10. **旧机娘迁移**：只做受管增量投影，还是逐步结构化完整旧档案？
11. **建筑升级政策**：哪些是逐实例改造，哪些研究完成即全局生效？
12. **动态档案导出**：如何安全回写设计态基线，是否只提供导出而不自动合并？
13. **解锁批次保留期**：叙事未消费的系统回执最多保留几轮，何时只转入通知中心？
14. **重点科技排序权重**：玩家钉选、直接后继、新路线和当前战略需求如何确定性打分？
15. **通知合并窗口**：同一结算点、多队列同秒完成与连续完成事件按什么边界合批？
16. **封存页回访政策**：仅警告并禁登记，还是阻止该页参与后续 normal 生成？
17. **动态科技正史化**：导出审阅包的字段、证据和驾驶员批准格式。

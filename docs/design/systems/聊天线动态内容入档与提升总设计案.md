## 1. 第一章 · 立项动机与病根

### 1.1 病根：LLM 无「完整新实体入世界书」通道

现有五标签词表（parsePipeline.ts:1910 `['战况','图鉴','初始状态','机娘档案','数据更新']`）逐一核对：

| 通道 | 能力 | 缺口 |
| :--- | :--- | :--- |
| `<图鉴>` → codex | 索引级摘要（name/kind/desc/params），schema.ts:109-120 明注「完整设定走世界书」 | **没有走的路**——完整设定无处安放，只能滞留 desc 一两句话 |
| `<数据更新>` → worldbookDataFiler | 补丁**既有条目**的 `<数据>` 块 | 新实体两处查无 → `findTargetEntry` 定位失败即 quarantined（worldbookDataFiler.ts:365-373），永远进不了世界书 |
| `<机娘档案>` → girlFiler | 完整入档（已改挂聊天书，CTRL-CHATBOOK-IMPL-01） | 机娘专用，非机娘实体不适用 |

后果：剧情里 LLM 捏出「等离子脉冲炮」这类新科技，只有 codex 里一行摘要；后续楼层 LLM 自己都读不到完整设定（世界书无条目、变量树不滞留大文本），设定漂移不可避免。

### 1.2 本案补齐的三件事

1. **新实体入档通道**：`标签 → pending 暂存 → filer 经守卫写聊天书`（复用 pending_lore→girlFiler 已验证管线的形制）；
2. **补丁双轨分流**：`<数据更新>` 语义按目标归属自动分流（落地 CHATBOOK-01 §8 Parking 第一项）；
3. **提升机制**：聊天书条目 → 玩家自命名独立全局书的显式晋升操作。

### 1.3 API 事实基座（已核验，出处标注）

| 能力 | API | 出处 | 置信度 |

### 2.1 管线形制（复用 pending_lore 先例，🔴 冻结）


### 2.2 暂存结构（schema 提案，实现时冻结字段名）

```text
ExpansionDossier {
  name: string                      // 实体名（实体对齐 applyAlign 复用）
  kind: '科技'|'建筑'|'载具'|'人员'|'装备'   // 对齐 CodexEntry.kind（'阵营'/'其他'不进本通道）
```

## 3. 第三章 · 补丁双轨分流（Q2=A · 归并 CHATBOOK-01 §8 Parking 第一项）

### 3.1 分流三规则（🔴 冻结）

`<数据更新>` 补丁的目标条目解析顺序与落轨：

```text
规则① 目标 ∈ 当前聊天档案书（先查）
        → 聊天轨：经 chatBookGateway 三重守卫后 updateWorldbookWith(聊天书)
          补丁本线产物（含 §2 新实体条目的 data 块与改挂后的机娘条目）
规则② 目标 ∈ 全局设定书（后查）
        → 全局轨：现行 worldbookDataFiler 行为原样（Diff 审核门/红线校验/热重算零改动）
规则③ 两处查无
        → 不走补丁管线，quarantined 留痕提示「新实体请走 §2 入档通道」
```

- **先聊天后全局**：聊天线改装优先命中本线产物（同名时聊天书条目遮蔽全局条目——本线的「等离子坦克改装」不该改到全局设定书）；
- 分界线由「条目已存在于哪本书」这一可机读事实承载，零新状态、零猜测、零自建映射；
- 语义对账：全局轨＝全局设定演化（CHATBOOK-01 §4.2 原语义），聊天轨＝聊天线增量——两语义在机读层面即三规则，不再需要人为判断。

### 3.2 继承关系明文

- CHATBOOK-01 §4.2「worldbookDataFiler v1 零改动」的不动区时效**至本案 confirmed 为止**；§8 Parking「worldbookDataFiler 全局/聊天双轨分流」**就地归并进本案，不再独立立项**；
- 全局轨的 Diff 审核门（PanelDataPatches 三通道裁决＋Auto-Apply 默认关）语义零改动；聊天轨是否同过 Diff 审核门：**是**——审核门是补丁管线的质量闸，与落轨无关，两轨同门。

## 4. 第四章 · 提升机制（Q3=组合案 · 🔴 冻结语义）

### 4.1 语义合同

- **移动，非复制**：提升成功后聊天书删原条目，独立书为该内容此后的唯一真源。理由：复制会造成同 key 双条目，提升书全局启用后本聊天双激活重复注入（可预见的 prompt 污染）；
- **玩家私产书**：书名与条目名用户自取，UI 自动填建议名（书名 `红警扩展·{条目名}`，条目名沿用原 comment 去前缀）；**不进角色卡 primary/additional 绑定**（那是卡的设计态资产）；
- **默认进全局启用列表**（`rebindGlobalWorldbooks` 追加，worldbook.d.ts:19），提供「暂不启用」选项；
- **显式用户操作**：提升是管理页授权写，属守卫体系外的用户显式操作（对齐 CHATBOOK-01「删除是显式操作」先例）；删的是**条目**非书，不触碰「零自动删书」红线。

### 4.2 提升流程（先建后删，fail-closed）

```text
① 预检：目标书名 ∉ getWorldbookNames()（撞名拒绝换名，§1.3 红线）；
② createWorldbook(新书名, [条目])——条目正文逐字节搬迁，comment 换用户所取名，
   extra 记 provenance（源聊天 chatId/源 comment/提升时刻，worldbook.d.ts:142）；
②′（F8 修订，2026-09-25）立即落盘新书：loadWorldInfo → saveWorldInfo(name, data, true)，
   失败 fail-closed（不删原条目）；
③ 默认 rebindGlobalWorldbooks([...现列表, 新书名])；
④ 复验新书 ∈ getWorldbookNames() 且条目在（缓存＋服务端 /api/worldinfo/get 回读双验）——全过才走 ⑤；
⑤ deleteWorldbookEntries(聊天书, 原条目)（经守卫确认聊天身份后执行），删除后立即落盘聊天书。
```

#### 4.2.1 持久化约束（F8 · CTRL-PROMOTE-PERSIST-01 冻结）

- **ST 保存语义**：TavernHelper `createWorldbook` 仅「空书」立即落盘（ST `createNewWorldInfo` 内部 `saveWorldInfo(..., immediately=true)`）；其后的条目写入走 `saveWorldInfo` 非立即分支 → ST world-info.js 的 **`saveWorldDebounced` 全局单例防抖（1000ms、不区分书名、last-args-wins）**。防抖窗口内任何他书非立即写入都会覆盖丢弃待保存的新书条目；且 `saveWorldInfo` 同步刷新 `worldInfoCache`，故 `getWorldbook` 当场复验不可信。
- **因此冻结两点**：①任何「建书带条目」或「改条目」写入后，若需跨刷新持久，须紧随一次 `saveWorldInfo(name, data, true)` 立即落盘（早于任何他书写入）；②复验持久性须绕过缓存，经 `/api/worldinfo/get` 服务端回读对比条目正文。
- **对既有五步流语义的影响**：②′与⑤落盘为纯加法，不改变五步先立后删的顺序与守卫；TH `render:'debounced'|'immediate'` 选项只影响编辑器渲染，与落盘无关。

- 任一步失败即停：**绝不先删后建**；④⑤ 间失败产生「已建未删」半程态 → 管理页警示双份存在＋提供「重试删除」，不自动收拾；
- `$promoted` chat 变量注册表（照 systemCheck.ts:410-455 `$archive` 先例）：记录 `{条目名 → 提升书名, 时刻}`——**advisory 元数据非绑定真源**（丢失最坏后果＝分叉警示失效，不影响任何写入正确性；不违反「零自建 chatId→书名映射」红线，该红线管的是聊天↔书绑定真源）。

### 4.3 提升后同名内容再生长：分叉＋警示（v1）

- 聊天线继续生长同名内容 → **照常入聊天书**（分叉），expansionFiler 入档时查 `$promoted` 命中则在回执与管理页打「已提升实体的本线分叉」警示标记；
- **悬挂记录降级（F8 修订，实现状态=`forkWarning:false`＋`forkStale:true`）**：`$promoted` 记录指向的目标书已不在世界书名单（被删/改名）时，分叉警示降级为提示级；名单不可用（预览环境）则保持原 advisory 语义。注册表本身永不自动改写/清理，由驾驶员人工裁决；
- 「同步进提升书」需二段审核，v1 不做，进 §8 Parking；「锁定禁写」剥夺剧情自由度，否决。
